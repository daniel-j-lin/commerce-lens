# CommerceLens v0.2.0 — Governed Coverage & Retained Evidence

## English

### 1. What's new

CommerceLens v0.2.0 adds governed `USER_DECLARED` source coverage, a consolidated
confirmation experience, exact proposal-fingerprint binding, and an explicit
retained-evidence lifecycle while preserving the Public v0.1 analytical scope.

### 2. Governed coverage authority

Mapping confirmation remains separate from coverage confirmation. Request dates,
observed source dates, filenames, and plausible export shape do not establish
coverage. A complete reviewed proposal may create `USER_DECLARED` authority only
after explicit confirmation and deterministic validation. CommerceLens does not
independently verify the declared source completeness.

### 3. Consolidated confirmation UX

Resolved export facts are displayed once in a declarative proposal. Only
missing, ambiguous, or contradictory facts trigger clarification. A plain
affirmative such as `確認` is normalized to the canonical confirmed intent; no
special coverage phrase is required. Confirmation is bound to the exact
proposal fingerprint, so stale or mismatched confirmation fails closed.

### 4. Retained evidence

Temporary execution remains the default. An explicit retention request enters
the formal retained workflow. `retained_complete` is emitted only after
persistence integrity succeeds and the completion marker is written. Retained
runs support cross-process `list`, `inspect`, and `verify`. Retention does not
change `ClaimDecision` or upgrade source authority.

### 5. Reliability / fail-closed behavior

Unknown coverage remains blocked with zero supported material claims. Ambiguous
cutoffs, incomplete proposals, stale fingerprints, unsupported status mappings,
and retention finalization failures do not produce false authority or false
completion. Diagnostic “why” requests continue to receive the governed refusal:
`Insufficient evidence to conclude why Revenue declined.`

### 6. Verification

The candidate is gated by deterministic coverage and retention tests, packaging
and diagnostic regressions, bilingual README parity, P15 preflight, the complete
test suite, diff and data-safety checks, and isolated fresh-install verification.
Exact results are recorded in the local release closeout rather than claimed in
advance by these notes.

### 7. Supported scope

Supported public metrics remain Revenue, Orders, AOV, and absolute Revenue
Change over governed CSV/XLSX sources with grouping `NONE`. Positive material
claims remain descriptive. `public_v0_1` identifiers remain compatibility
identifiers and are not product-version authorities.

### 8. Limitations

CommerceLens does not support positive diagnostic or causal explanations,
forecasting, recommendations, Revenue Change Percentage, product/category
contribution, vendor connectors, hosted SaaS, or a REST API. Local retained
storage is plaintext with no TTL, encryption, or secure erase. `USER_DECLARED`
is not independent verification.

### 9. Validation status and next step

Internal protocol rehearsal completed.

P00 passed as an internal expert rehearsal with zero external participants.
P15 remains NOT PASS. P01 external first-user validation remains next. This
release does not claim external user validation, production readiness, proven
usability, enterprise security, or product-market fit.

## 繁體中文

### 1. 新增內容

CommerceLens v0.2.0 新增受治理的 `USER_DECLARED` 來源 coverage、整合式確認
體驗、精確的 proposal-fingerprint 綁定，以及明確的 retained-evidence lifecycle，
同時維持 Public v0.1 的分析範圍。

### 2. 受治理的 coverage authority

Mapping 確認仍與 coverage 確認分開。請求日期、來源中觀察到的日期、檔名與看似
合理的匯出形態都不能建立 coverage。完整且經檢視的 proposal 只有在明確確認與
確定性驗證後，才可建立 `USER_DECLARED` authority。CommerceLens 不會獨立驗證
所宣告的來源完整性。

### 3. 整合式確認 UX

已確定的匯出事實只會在 declarative proposal 中顯示一次；只有缺漏、模糊或
矛盾的事實會觸發澄清。一般肯定回覆如 `確認` 會正規化為 canonical confirmed
intent，不需要特殊 coverage 詞句。確認會綁定精確的 proposal fingerprint，因此
過期或不相符的確認會 fail closed。

### 4. Retained evidence

Temporary 執行仍為預設。明確的 retention 要求會進入正式 retained workflow。
只有 persistence integrity 成功且 completion marker 寫入後，才會輸出
`retained_complete`。Retained run 支援跨程序 `list`、`inspect` 與 `verify`。
Retention 不會改變 `ClaimDecision`，也不會提升來源 authority。

### 5. 可靠性／fail-closed 行為

未知 coverage 仍會被阻擋，且支援的實質主張為零。模糊 cutoff、不完整
proposal、過期 fingerprint、不支援的 status mapping，以及 retention finalization
失敗，都不會產生虛假 authority 或虛假完成狀態。診斷性的「為什麼」問題仍使用
治理後的拒絕：`Insufficient evidence to conclude why Revenue declined.`

### 6. 驗證

Candidate 必須通過確定性的 coverage 與 retention 測試、packaging 與 diagnostic
regressions、雙語 README parity、P15 preflight、完整 test suite、diff 與
data-safety checks，以及 isolated fresh-install verification。精確結果會記錄在本機
release closeout，而不會由本 release notes 預先宣稱。

### 7. 支援範圍

公開 metrics 仍為 Revenue、Orders、AOV 與絕對 Revenue Change，來源為受治理的
CSV/XLSX，grouping 為 `NONE`。正向實質主張仍限於描述性內容。`public_v0_1`
識別符仍是相容性識別符，不是產品版本權威。

### 8. 限制

CommerceLens 不支援正向診斷或因果解釋、forecasting、recommendations、Revenue
Change Percentage、產品／類別 contribution、vendor connectors、hosted SaaS 或
REST API。本機 retained storage 是明文，沒有 TTL、加密或安全抹除。
`USER_DECLARED` 不等於獨立驗證。

### 9. 驗證狀態與下一步

內部 protocol rehearsal 已完成。

P00 已作為內部專家 rehearsal 通過，外部參與者為零。P15 仍為 NOT PASS。
下一步仍是 P01 外部 first-user validation。本 release 不宣稱外部使用者驗證、
production readiness、已證明的 usability、enterprise security 或 product-market fit。
